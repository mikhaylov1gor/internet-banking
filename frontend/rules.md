фронтовое приложение состоит минимум из 3х слоёв:
UI
бизнес-логика (use-cases/сценарии)
слой взаимодействия с сервером
при этом слой взаимодействия с сервером должен быть разделён на два слоя: сетевой слой, который содержит в себе (инкапсулирует) всю логику работы с запросами по сети; а также слой, который содержит бизнес-логику отправки запросов и обработки ответов.
слои не смешиваются (UI не делает fetch напрямую, сетевой слой не знает про UI и т.д.)
В UI слое должен быть выделен слой переиспользуемых компонентов, которые не зависят от конкретных страниц и бизнес-сценариев.
Повторяющиеся паттерны UI (модалки, подтверждения, формы, таблицы) должны использовать общие базовые компоненты/обёртки/конфигурирование, а не копипаст.

На фронтенде  должен быть единый механизм обработки ошибок в виде иерархии/конвейера, где ошибки обрабатываются на подходящем уровне (компонент/страница/глобальный обработчик и тд), а необработанные приводят к fallback-странице.

На стороне фронтенда должен быть типобезопасный контракт взаимодействия с сервером: DTO запросов/ответов должны быть строго типизированы, использование any (и аналогичных обходных путей типизации) запрещено. Парсинг через zod схему
Любое пользовательское действие в интерфейсе должно иметь явную реакцию приложения: отображение статуса выполнения (например, загрузка/ожидание), успешное завершение или сообщение об ошибке. Запрещены “тихие” ошибки, когда пользователь не понимает, произошло ли действие.
Единообразный механизм отображения состояний и уведомлений.
Не должно быть комментариев и не используемого кода
Не использовать тип React.FC, типизировать пропсы в аргументе ({ ... }: Type)
Не использовать интерфейсы, а использовать Типы
